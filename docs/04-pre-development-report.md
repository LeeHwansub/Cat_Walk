## 2. 기술 스택 제안 (D-13)

### 권장안: Vite + TypeScript + Three.js (React 없이)

| 영역 | 선택 | 이유 |
|---|---|---|
| 빌드·개발 서버 | Vite | 설정이 거의 없고 실행이 빠르다 |
| 언어 | TypeScript | 기획서 17.3 "TypeScript 우선" |
| 3D 렌더링 | Three.js | 브라우저 3D 표준 라이브러리. 카메라·조명·그림자 직접 제어 |
| 카메라 조작 | Three.js 내장 `OrbitControls`(examples) 또는 직접 구현 | 추가 패키지 없음 |
| 상태 관리 | 별도 라이브러리 없음. 작은 `GameState` 객체 + 이벤트 | 상태가 적다(외형, 모드, 배고픔, 설정) |
| 캐릭터 애니메이션 | 코드로 만드는 절차적 애니메이션 (관절 회전 보간) | D-14와 연결. 그루밍처럼 무료 에셋에 없는 동작을 만들 수 있다 |
| 저장 | `localStorage` (JSON + 버전 필드) | 기획서 11장 |
| 사운드 | Web Audio API | 추가 패키지 없음 |
| UI | HTML/CSS 오버레이 | 화면 4개(시작, 생성, 플레이 HUD, 설정)로 충분 |
| 테스트 | Vitest (로직만: 행동 선택, 배고픔, 저장) | Vite와 설정 공유 |

**추가할 의존성 (승인 필요):** `three`, `@types/three`, `vite`, `typescript`, `vitest` — 5개

**TypeScript 버전 주의:** 최신 `typescript` 7.x는 새 컴파일러로 바뀐 메이저 버전이다. Vite·Vitest 도구와의 호환성은 **확인하지 않았다.** 설치할 때 실제로 타입 검사를 실행해 보고, 문제가 있으면 5.x로 고정할 것을 제안한다.

### 대안: React + React Three Fiber + drei
- 장점: 선언형 컴포넌트, drei의 카메라·컨트롤 도우미, React UI와 자연스럽게 통합
- 단점: 의존성이 늘어난다(react, react-dom, fiber, drei 등). 행동 AI 같은 매 프레임 게임 루프 로직은 결국 `useFrame` 안에 명령형으로 쓰게 되어 이점이 줄어든다. 1일 MVP에서는 배우고 디버깅할 층이 하나 더 생긴다.
- 대안이 더 나은 경우: 이후 UI(커스터마이징 화면, 설정)가 크게 복잡해질 때

## 3. 프로젝트 폴더 구조 (제안)

기존의 빈 `web/` 폴더를 앱 루트로 사용한다.

```
web/
├─ index.html
├─ package.json / tsconfig.json / vite.config.ts
├─ public/assets/sounds/          # 사운드 파일 (D-15)
├─ src/
│  ├─ main.ts                     # 진입점: 화면 전환, 게임 시작
│  ├─ core/                       # 게임 루프, 시간, 입력(WASD), 이벤트
│  ├─ world/                      # 씬, 조명, 그림자
│  │  └─ map/                     # 주택가 골목, 공원, 충돌 영역, 관심 지점
│  ├─ cat/                        # 고양이 모델 생성, 외형 적용, 관절 애니메이션, 이동
│  ├─ behavior/                   # 자율 행동 선택기 + 행동별 파일 (걷기, 앉기, 둘러보기, 냄새, 그루밍, 낮잠, 먹기)
│  ├─ camera/                     # 3인칭 추적(회전·줌), 캣캠 1인칭, 전환
│  ├─ systems/                    # 배고픔, 먹이, NPC
│  ├─ audio/                      # 사운드 재생, 반복 방지, 음소거
│  ├─ save/                       # localStorage 저장·불러오기
│  └─ ui/                         # 시작, 고양이 생성, HUD, 설정 화면
└─ tests/                         # 행동 선택, 배고픔, 저장 단위 테스트
```

책임 분리 원칙:
- `behavior/`는 "무엇을 할지"만 정하고, `cat/`은 "어떻게 움직일지"만 맡는다. 직접 조작 모드에서는 입력이 `behavior/`를 건너뛰고 `cat/`을 직접 움직인다.
- 맵은 데이터(건물 위치, 이동 가능 영역, 풀밭·화단 같은 관심 지점)와 렌더링을 나눈다. 자율 행동이 관심 지점을 읽어서 "풀밭이 있으면 뒹군다" 같은 환경 반응을 만든다(기획서 5.4).

## 4. MVP 구현 계획

기획서 16장 STEP 5 순서를 따르되, **항상 실행 가능한 상태를 유지하도록** 기능 단위로 나눈다. 각 단계 끝에 브라우저에서 확인한다.

| 단계 | 작업 | 완료 확인 |
|---|---|---|
| 1 | 프로젝트 초기 설정 (Vite + TS + Three, 테스트 실행 확인) | `npm run dev` 빈 화면, `npm test` 통과 |
| 2 | 3D 환경: 바닥, 햇빛, 그림자, 하늘색 | 씬이 보인다 |
| 3 | 고양이 모델 (도형 조합 로우폴리, 털색·무늬 적용 구조) | 고양이가 보인다 |
| 4 | 이동: WASD + 걷기 애니메이션 + 이동 가능 영역 | 키보드로 걷는다 |
| 5 | 카메라: 눈높이 3인칭 추적, 회전·줌, 캣캠 전환 | 시점 전환이 매끄럽다 |
| 6 | 자율 행동: 걷기, 앉기, 둘러보기, 냄새 맡기, 낮잠, 꼬리 흔들기 | 손대지 않아도 움직인다, 같은 행동만 반복하지 않는다 |
| 7 | 그루밍: 앞발 핥기 → 얼굴 닦기 | 휴식 중에 가끔 그루밍한다 |
| 8 | 자동/직접 조작 전환 (입력이 멈추면 몇 초 뒤 자동 복귀) | 끊김 없이 전환된다 |
| 9 | 맵: 주택가 골목 + 작은 공원 (도형 기반 건물, 담장, 차, 나무, 벤치, 연못) | 동네를 돌아다닐 수 있다 |
| 10 | 배고픔(압박 없음) + 먹이 공간 + 주민 NPC 1명 | 먹으면 회복, 0이어도 제한 없음 |
| 11 | 사운드: 야옹 2~3종, 골골송, 환경음, 전체·울음 음소거 | 재생·음소거가 된다 |
| 12 | UI: 시작, 고양이 생성, HUD(배고픔·모드·설정 버튼), 설정 | 기본 흐름이 이어진다 |
| 13 | 로컬 저장 | 새로고침 후 설정이 유지된다 |
| 14 | 테스트 및 수정 (기획서 STEP 6 항목 전체) | 18장 완료 기준 체크 |

검증: 단위 테스트(Vitest, 로직), 타입 검사(`tsc --noEmit`), 프로덕션 빌드(`vite build`), 브라우저 수동 확인(18장 체크리스트).

## 부록 A. 고양이 모델 사실성 높이기 (D-14 상세, 2026-11-04 추가)

### A.1 "사실적으로 보이는" 요소 4가지
| 요소 | 내용 | 체감 효과 |
|---|---|---|
| 형태 | 실루엣, 비율(작은 머리·긴 몸·가는 다리), 부드러운 곡면 | 중 |
| 표면 | 털 질감, 무늬 텍스처, 부드러운 조명 반응 | 중 |
| 움직임 | 척추 곡선, 발 디딤, 꼬리·귀의 2차 움직임, 숨쉬기, 눈 깜빡임 | **높음** |
| 행동 | 멈춤, 망설임, 둘러보기 타이밍 | **높음** |

움직임과 행동은 어떤 모델 방식을 고르든 코드로 만드는 영역이다. 기획서 19장의 1순위 "자연스러운 움직임"도 이쪽이다.

### A.2 방식별 비교
| 방식 | 사실성 | 그루밍 등 동작 | 털색·무늬 커스터마이징 | 일정 | 비용·승인 |
|---|---|---|---|---|---|
| ① 코드 도형 모델 (기존 권장) | 낮음 | 자유롭게 만들 수 있음 | 쉬움 | 짧음 | 없음 |
| ①+ 코드 모델 고급화 (곡면 몸체, 셸 텍스처링 털, 절차적 2차 움직임) | 중하 | 자유롭게 만들 수 있음 | 쉬움 | +2~3h (추정) | 없음 |
| ② 무료 리깅 모델(glTF) + 코드로 뼈대 애니메이션 | 중~높음 | 기본 동작은 모델에 포함, 그루밍은 코드로 뼈를 회전해 추가 | UV 기반 무늬 마스크 필요 | +1~3h (검색·검증 포함, 추정) | 라이선스 확인 필요 (CC0 또는 CC-BY 출처 표기) |
| ③ 유료 사실적 모델 (그루밍 애니메이션 포함 상품) | 높음 | 상품에 따라 다름 | 상품에 따라 다름 | 포맷 변환 시간 | 구매 승인 필요 |
| ④ AI 3D 생성 서비스 (사진 → 메시) | 중 (외형만) | 리깅 별도 필요 | 사진마다 다름 | 리깅 때문에 길어짐 | 외부 서비스 승인, 이용약관 확인 |
| ⑤ Blender 직접 모델링·리깅 | 높음 | 자유롭게 만들 수 있음 | 자유롭게 만들 수 있음 | 하루 MVP에는 맞지 않음 | 작업자 필요 |

특정 무료·유료 모델이 실제로 있는지, 라이선스와 동작 구성이 어떤지는 **아직 조사하지 않았다.**

### A.3 주의점
- 완전한 사실주의는 기획서 15장의 "귀엽지만 유치하지 않은 디자인"과 맞지 않을 수 있다. 어설프게 사실적인 고양이는 오히려 어색해 보일 수 있다(불쾌한 골짜기). 목표는 **"반사실적(semi-realistic)"**을 제안한다.
- 사실적인 메시일수록 털색·무늬 5종을 바꾸기 어렵다. 텍스처 마스크를 설계해야 한다.
- 캣캠 시점에서는 앞발 모델이 화면에 크게 보이므로 앞발 품질이 중요하다.

### A.4 제안
- **MVP:** ②를 1~2시간 안에 찾아보고, 조건(CC0/CC-BY, glTF, 걷기·앉기·눕기 포함, 수정 허용)에 맞는 모델이 없으면 ①+로 진행한다.
- **구조:** `cat/` 모듈은 "모델 공급자"를 교체할 수 있게 만든다. 행동·애니메이션 코드는 "머리, 척추, 다리, 꼬리" 같은 추상적인 관절에 명령하고, 도형 모델과 리깅 모델이 각각 그 명령을 해석한다. 이렇게 하면 나중에 ③이나 ⑤로 바꿔도 행동 시스템을 다시 만들지 않아도 된다.
